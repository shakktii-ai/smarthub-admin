smarthub-admin — the panel in one file

Next.js 14 App Router, JavaScript (no TypeScript), four role dashboards on one FastAPI backend. This is the doc of record for the admin panel; README.md is not — it still says "No backend, database or real auth", which stopped being true when the panel was re-pointed at the backend REST API.
Master doc Backend Merchant Borrower Admin panel

What this panel is

The operations back office. Staff sign in with an email and password, land on the dashboard their backend role decides, and run the business: approve merchants, decide refunds, reconcile settlements, chase overdue loans, publish app content, send campaigns. It renders no money math of its own — every number is the backend's, and every write is an HTTP call the backend authorises again.

The one fact that decides everything else. There is exactly one data seam. UI code imports @/services and nothing else; services/index.js chooses the implementation from API_CONFIG.useMocks, which is a build-time constant read from NEXT_PUBLIC_USE_MOCKS. In a real build that is false, the mock module is never imported, and every call goes to FastAPI. If a screen shows data that no backend endpoint can produce, the build was made with mocks on — check the Network tab before believing a screenshot.
Not a test suite. There is no test runner in package.json — only dev, build, start. Verification of this panel is the build, the lint-free read, and probing the deployed API. Nothing here is "proven by tests".

The four dashboards

One app, four navigation trees, chosen by the role claim in the backend's access token. The mapping is in config/auth.js; the nav arrays are in config/dashboards/*.js; the table configs are in data/pages/*.js.

Roles arrive UPPER_SNAKE and are lower-cased. pickDashboardRole() normalises the backend's SUPER_ADMIN-style claims before they are matched against ROLES. A new backend role needs an entry in ROLES here, or the holder is refused a dashboard at sign-in with "no assigned dashboard".
Access is strict-prefix, on purpose. canAccessPath(role, path) allows only the role's own prefix plus EXTRA_ACCESS, and EXTRA_ACCESS is { super_admin: [] } — empty. A Super Admin cannot open a Merchant Admin URL. That is the deliberate choice; if you ever widen it, do it in that one object and nowhere else. It is also the reason approve this merchant looked missing: the review screen existed, behind a prefix this role cannot reach. The fix was /super-admin/applications and prop-driven components, not a looser ACL — EXTRA_ACCESS is still empty.

Screen map, with what each one really is

"Config table" means <ResourcePage dashboard pageKey> reading data/pages/<role>.js → a resource in services/api/resources.js → one backend endpoint. "Hand-written" means a component that calls @/services directly. "Server action" means a 'use server' file that authorises and calls the backend itself, bypassing the seam by design.

The data seam, end to end

  1. services/index.js exports 32 named functions, each one (await impl()).fn(...) where impl picks ./mock or ./api. Adding a call means adding one line here and the same-named export in both implementations — that is the tax, and it is what keeps a mock build honest. The four added with the app-content/inbox pass are updateRecord, deleteRecord, getEditValues and searchRecords. One seam export is already broken in a mock build: the API file defines verifyBank, the mock defines runPennyDrop, both are re-exported here, and components/onboarding/ApplicationDetail.jsx imports verifyBank — so with NEXT_PUBLIC_USE_MOCKS=true the bank-verification tab throws.
  2. services/api/resources.js declares 40 resource records, the c_* and sa_* alias keys counted inside that number — each a path, a shape, which filters/query params it supports, how a backend row becomes a UI row, and what the create/edit form sends. They reference 23 distinct /api/*/v1 namespaces.
  3. services/api/index.js implements the seam functions against those records. Lists are fetched in pages of 200 and sliced in memory, capped by MAX_ROWS = 1000, because FastAPI caps limit per route (200 on most lists, 500 on some) and a single oversized request would silently return a partial set and make every other tab read zero. searchRecords is the deliberate opposite: one bounded page, server-side q when the resource declares it supports, because a picker that asks "which merchant do you mean?" while the operator types must not re-pull the whole directory per keystroke.
  4. components/ResourcePage.jsx renders the table, tabs, filters, stats and the create/edit form from the page config, with CSV export named <resource>-YYYY-MM-DD.csv. It now also renders Edit and Delete whenever the config declares them (config.edit, whose skip list drops fields the PATCH cannot take, and config.delete.confirm) — the generic renderer, not per-screen code, which is why app content was the first pair and campaigns the second. Two screens have since left it: merchants, because a directory with lifecycle buttons is not a config table, and legal documents, because a policy is not a row — a JSON textarea is the wrong control for prose. Edit pre-fills from row.raw through RESOURCES[resource].forEdit, never from the table: the display columns are lossy on purpose (Yes/No, Web: https://…) and writing those words back to an enum column is how a row gets corrupted.
  5. UNMAPPED is the honesty list: keys with no backing endpoint. Today it holds exactly one — inventory, because /api/devices/v1 tracks paired devices, not purchase stock. A key listed there shows "no endpoint yet" instead of a fabricated number.
Backend timestamps are naive UTC. resources.js reads every timestamp through utcDate() before formatting. Without it a "Today" filter and an "Expired" label are wrong by the local offset — which is exactly how a published app-content row can look live to one person and expired to another. Writing is the mirror image and needs two different helpers: utcWallClock() turns what the operator typed into UTC for the request, and localWallClock() turns the stored value back into the wall clock a datetime-local box expects. Pre-fill an editable schedule window with the raw stored value and every edit drifts the window by five and a half hours.
Paging is client-side above the fetch. The panel pulls up to 1000 rows and pages them in the browser. That is fine for the volumes today and wrong for a large merchant: the fix is a server-paged resource shape, not a bigger MAX_ROWS.

Login, cookies and who actually checks permission

The backend owns sessions. This panel only stores the tokens it is given and presents them; it never issues, edits or trusts its own notion of a user.

Sign-in

app/login/actions.js → lib/auth/backend.js
  • POST /api/identity/v1/login with application/x-www-form-urlencoded — the backend takes an OAuth2PasswordRequestForm, not JSON.
  • Local validation first (email shape, password ≥ 6), then rateLimit("login:"+ip+":"+email, 8, 5 min). A failed response always calls clearSession() — a session is never written on a non-OK response.
  • If the backend replies mfa_required, the panel holds the mfa_token and asks for the authenticator code or a recovery code (ABCDE-12345), then POST /api/identity/v1/mfa/verify with the token in the body, not as a Bearer header. MFA attempts are rate-limited to 8 per 5 minutes. The verified response is read from result.data.access_token: lib/auth/backend.js::post() keeps the parsed body under data and never spreads it, so reading it off the wrapper is the difference between a working sign-in and a correct code that always fails.
  • If the backend replies 403 mfa_enrollment_required — the platform policy refusing an administrator with no authenticator — the form does not give up: it calls /mfa/enroll/start with the same credentials, draws the returned qr_svg, and completes with /mfa/enroll/complete, which opens the session and returns the recovery codes for a one-time download. The rate limit is per ip:email, and a mistyped code keeps the scanned key instead of issuing a new one.
  • The landing dashboard comes from the role claim inside the backend-signed access token, never from the form.

Two-factor, self-service

app/account/security → components/account/SecuritySettings.jsx
  • /account/security is one screen shared by all four roles: SHARED_PREFIX in config/auth.js lets canAccessPath pass it for any role, and app/account/layout.jsx wraps it in the sidebar of the signed-in profile — four copies would drift apart.
  • Enrol, verify, turn off, replace lost recovery codes. The QR is the backend's own SVG data URI, so the secret never reaches a renderer, a vendor or page script.
  • The policy is displayed as a fact (required_by_policy) because flipping MFA_REQUIRE_FOR_ADMINS changes how every administrator signs in; that is a deploy decision, not a dashboard toggle.
  • Recovery codes are shown once and then only counted, because the backend stores hashes.

Three cookies, two tiers

config/api.js → lib/api/server.js writeSession()
  • shp_access — JS-readable, because ResourcePage is a client component and attaches it as a Bearer token.
  • shp_refresh — httpOnly, never sent to the browser JS, spent only by the same-origin /api/session/refresh. Its cookie age is matched to the refresh token's own exp claim, falling back to 7 days.
  • shp_session — a non-secret "1" marker so client code and middleware know a refresh cookie exists without being able to read it.
  • All three: path=/, sameSite=lax, secure only when NODE_ENV=production.

Rotation and revocation

app/api/session/refresh/route.js, lib/api/browser.js
  • Browser code calls POST /api/session/refresh — a route in this app, which reads the httpOnly cookie, calls POST /api/identity/v1/refresh, writes the new pair and returns only the access token.
  • Any refresh failure clears the session and answers 401, so a revoked refresh token logs the user out rather than looping.
  • signOut() calls POST /api/identity/v1/logout with the refresh token and then clears cookies — the backend revokes the session; the panel only forgets it.

Server-side re-check

lib/auth/session.js
  • getCurrentProfile() is wrapped in React cache() and calls GET /api/identity/v1/me on every request. Null if there is no usable session, if the reply is inactive, or if the role is not a dashboard role.
  • authorize(roles) is the gate every server action starts with: 401 "Please sign in again." with no profile, 403 with the wrong role, otherwise { profile, api } where api is the server client.
  • Tenancy: organization_id is filled from branch_code — the Supabase-era key kept so page code did not have to be rewritten. merchant_code travels alongside it.
middleware.js decodes the JWT but does not verify its signature. Its own comment says so: it is a routing hint that picks a landing page and bounces a role out of a URL it cannot see. Anyone with a forged shp_access can reach a page component. What contains the damage is that every read goes back through serverApi or a Bearer call the backend re-verifies (signature, expiry, revocation, role), and server actions call authorize() which re-reads /me. Consequence if a future screen renders data from a client component without a backend call: it would be showing unauthenticated input. Keep that shape impossible.
rateLimit() is a per-process Map. Good for one instance; with several Next.js instances the window is per instance, and it is wiped on restart. The backend already has durable rate limiting — this one is only the sign-in form's local brake.

What the panel can change, and what it can only look at

Dangerous writes are two-step by construction. Status changes in the page configs go through set(), which attaches a confirm message naming the rule: "This writes to the backend. A checker (a different user) must approve sensitive actions in production." The panel does not decide that by itself — it calls the backend, which holds the maker-checker queue and the ledger. The panel's job is to never make an action look reversible when it is not.
Refund decisions and reject notes are the backend's contract. The panel sends what the endpoint asks for; a decision without a note is accepted or refused by the backend, not here. The 500 that used to happen when RefundDecisionRequest.note was missing was fixed on the backend side, so the panel sends the field and does not compensate.

The service health strip

Six states, all derived by the backend from traffic it actually saw, none of them a config flag. components/superadmin/ServiceHealth.jsx is the single reader.

  • POLL_SECONDS = 20, and the interval pauses while document.hidden — the one place in the panel that re-polls, because a health strip that never moves is the static picture this replaced.
  • Both the dashboard strip and CampaignStudio.jsx import useServiceHealth(), so the composer and the dashboard cannot disagree about whether WhatsApp is delivering.
  • drainNotificationQueue() is exposed next to it: a human can push the held backlog out once the channel is back.
  • The labels are the backend's words on purpose. disabled means the stub is wired instead of a vendor — which is what a panel showing "Stub" means when SMS_PROVIDER=stub. That is the truth about the deployment, not a bug in this screen.

Environment — names only

There is no .env.example in this repo and the live .env is not read here. These are the names the code actually references; values are the owner's to set.

Both are baked at build time, not read at runtime. NEXT_PUBLIC_* values are inlined into the bundle, so a production image built with NEXT_PUBLIC_API_BASE_URL=http://localhost:8000 talks to the laptop it was built on forever. The .next/ output in this working tree was built with https://api.smarthubpay.com inlined — useful as evidence of what a correct build looks like, and a reminder that the leftover build directory is not the deployed artefact.

Which backend namespaces this panel consumes

Counted from the paths referenced in services/api/resources.js — 22 namespaces through the resource layer. The KPI strip says 23 because that one counts every /api/*/v1 literal in the panel, including the routes server actions call directly, which is exactly how the reviewer surface reaches the backend. Read alongside the backend doc; the contract lives there.

The BFF split matters here. Collection screens call /api/collection-admin/v1 rather than the raw loan and payment features, so an agent sees only their own book and the scoping is one place. Merchant Admin lists use /api/merchant-admin/v1 where it exists and the raw feature where it does not — that asymmetry is the backend's current state, not a panel bug.
